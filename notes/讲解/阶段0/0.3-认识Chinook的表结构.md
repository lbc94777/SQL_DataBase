# 阶段 0：认识 Chinook 的表结构

## 全貌

这一篇回答三个问题：

1. **表、行、列分别是什么？** 一张表在数据库里到底长什么样？
2. **主键是什么？** 为什么每张表都需要它？
3. **怎么查看一张表的结构？** 拿到一个陌生的数据库，怎么弄清楚里面有什么？

为什么现在学：0.4 开始写查询，前提是知道库里有哪些表、每张表有哪些列、列里存的是什么。另外，主键这个概念从现在一直用到最后，阶段 1 设计选课系统的表时，第一件事就是给每张表选主键。

重点是**主键**和**看表结构的方法**。表和表之间怎么关联（外键）这次只需要认得出来，正式讲在阶段 1。

### 先指出两个容易误解的地方

> **你可能以为表里的行是有顺序的**，像 Python 的 list 一样有第 0 行、第 1 行。**其实关系数据库里的表没有固有的行顺序。** 不写排序要求时，返回的顺序由 DBMS 决定，不保证稳定。
>
> 可以自己验证：
> ```sql
> SELECT * FROM PlaylistTrack LIMIT 3;
> ```
> 结果是 `TrackId` 3402、3389、3390，并没有按大小排列。想要固定的顺序，必须明确要求（`ORDER BY`，0.4 会讲）。所以表里的行不靠"第几行"来区分，而是靠下面要讲的**主键**。

> **你可能以为主键就是"第一列"或者"名字叫 xxxId 的那一列"。其实主键是一条规则**，要用 `PRIMARY KEY` 明确声明，而且可以由**多列**共同组成。Chinook 里就有一张表的主键是两列，下面的任务会让你去找它。

## 表、行、列

从你熟悉的东西说起。假设用 C++ 存一批音乐曲目：

```cpp
struct Track {
    int    trackId;
    string name;
    int    milliseconds;
    double unitPrice;
};
vector<Track> tracks;
```

数据库里的**表**和这个很像：

- **列**相当于结构体的**字段**：有名字、有类型，所有行都具有相同的列。
- **行**相当于一个**结构体实例**：一条完整的记录，比如一首歌。
- **表结构**（schema）相当于 `struct` 的定义：规定了这张表有哪些列、每列是什么类型、有什么规则。

和 `vector` 不同的有两点：

1. 行没有下标，也没有固有顺序（上面已经验证过）。
2. 表结构上可以附带**规则**，比如"这一列不能为空"、"这一列的值不能重复"。DBMS 会强制执行这些规则，这就是 [为什么需要数据库](0.2-为什么需要数据库.md) 里"问题四"提到的约束。

## 主键：唯一确定一行

### 为什么需要主键

Chinook 的 `Customer` 表里，有两位顾客都叫 Frank，也有两位都叫 Mark。现在要"把 Frank 的邮箱改成某个新地址"，到底改哪一个？

行没有下标，名字又可能重复，所以需要一列（或几列）的值**在整张表里独一无二**，能精确地指出"就是这一行"。这就是**主键**。

### 主键的两条规则

- **唯一**：任意两行的主键值都不能相同。
- **非空**：每一行都必须有主键值。

这两条由 DBMS 强制执行。如果插入一行，它的主键值和已有的行重复，DBMS 会直接拒绝。0.8 做 `INSERT` 时可以亲眼看到。

### Chinook 的主键

Chinook 里几乎每张表都用一个**整数编号**当主键：`ArtistId`、`AlbumId`、`TrackId`、`CustomerId`……这些编号本身没有业务含义，只用来标识一行。

为什么不用名字、邮箱这类"有意义"的列当主键？这个问题留在任务里，让你先自己想。阶段 1 会正式讨论主键怎么选。

## 表和表之间：用 ID 互相引用

看 `Track` 表的前几行：

| TrackId | Name | AlbumId |
|---|---|---|
| 1 | For Those About To Rock (We Salute You) | 1 |

`AlbumId = 1` 是什么意思？去 `Album` 表找 `AlbumId` 为 1 的那一行：

| AlbumId | Title | ArtistId |
|---|---|---|
| 1 | For Those About To Rock We Salute You | 1 |

再去 `Artist` 表找 `ArtistId` 为 1 的那一行：

| ArtistId | Name |
|---|---|
| 1 | AC/DC |

所以 1 号曲目属于 1 号专辑，1 号专辑属于 AC/DC。

这正是 [为什么需要数据库](0.2-为什么需要数据库.md) 里"问题五"的解决办法：艺术家的名字**只在 `Artist` 表里存一份**，其他表只存它的编号。AC/DC 如果改名，只需要改一行。

`Track` 里像 `AlbumId` 这样"指向另一张表主键"的列，叫做**外键**。现在你只需要做到：看见表结构里的 `FOREIGN KEY ... REFERENCES ...`，知道它表示"这一列引用了另一张表"。外键的规则和设计在阶段 1 讲。

现在手动追踪要来回翻好几张表。阶段 3 学了连接查询（`JOIN`）后，一条 SQL 就能直接查出"曲目名 + 专辑名 + 艺术家名"。

## Chinook 是一家什么样的"店"

Chinook 模拟的是一家在线音乐商店，11 张表可以分成四组：

```
音乐目录：  Artist ──< Album ──< Track >── Genre（流派）
                                   └────── MediaType（文件格式）

销售：      Customer ──< Invoice ──< InvoiceLine >── Track
             （顾客）     （发票）     （发票明细）

员工：      Employee（Customer.SupportRepId 指向负责该顾客的员工）

歌单：      Playlist ──< PlaylistTrack >── Track
```

`A ──< B` 的意思是"一个 A 对应多个 B"，比如一个艺术家有多张专辑。这种画法在阶段 1 画 ER 图时还会用到，现在能看懂就行。

## 怎么查看表结构

拿到一个陌生的数据库，可以按下面的顺序摸清它。

### 1. 有哪些表：`.tables`

```
sqlite> .tables
Album          Employee       InvoiceLine    PlaylistTrack
Artist         Genre          MediaType      Track
Customer       Invoice        Playlist
```

### 2. 一张表的完整定义：`.schema 表名`

```
sqlite> .schema Track
CREATE TABLE [Track]
(
    [TrackId] INTEGER  NOT NULL,
    [Name] NVARCHAR(200)  NOT NULL,
    [AlbumId] INTEGER,
    ...
    CONSTRAINT [PK_Track] PRIMARY KEY  ([TrackId]),
    FOREIGN KEY ([AlbumId]) REFERENCES [Album] ([AlbumId])
		ON DELETE NO ACTION ON UPDATE NO ACTION,
    ...
);
CREATE INDEX [IFK_TrackAlbumId] ON [Track] ([AlbumId]);
```

它显示的是当初**创建这张表的 SQL 语句**。逐行来读：

- `[TrackId] INTEGER NOT NULL`：列名 `TrackId`，类型是整数，`NOT NULL` 表示不能为空。
- `[AlbumId] INTEGER`：后面没有 `NOT NULL`，说明**允许为空**，也就是某首曲目可以不属于任何专辑。
- `CONSTRAINT [PK_Track] PRIMARY KEY ([TrackId])`：声明主键是 `TrackId`。`PK_Track` 是给这条规则起的名字。
- `FOREIGN KEY ... REFERENCES ...`：外键，上面讲过。后面的 `ON DELETE NO ACTION ...` 先跳过，阶段 2 讲。
- `CREATE INDEX ...`：索引，阶段 5 讲，现在跳过。

另外有三个小细节，看到时知道是怎么回事就行：

- **方括号**，比如 `[Track]`，是给名字加引号的一种写法（来自微软 SQL Server 的风格），和直接写 `Track` 效果一样。你自己写 SQL 时不用加。
- `NVARCHAR(200)` 意思是"最长 200 个字符的文本"。但 SQLite 对类型很宽松，并不真的检查长度。阶段 2 会专门讲这个特点。
- **SQL 关键字不区分大小写**，`SELECT` 和 `select` 一样。习惯上关键字用大写，表名和列名按原样写。

### 3. 更整齐的列清单：`PRAGMA table_info(表名);`

```
sqlite> PRAGMA table_info(Track);
╭─────┬──────────────┬───────────────┬─────────┬────────────┬────╮
│ cid │     name     │     type      │ notnull │ dflt_value │ pk │
╞═════╪══════════════╪═══════════════╪═════════╪════════════╪════╡
│   0 │ TrackId      │ INTEGER       │       1 │            │  1 │
│   1 │ Name         │ NVARCHAR(200) │       1 │            │  0 │
│   2 │ AlbumId      │ INTEGER       │       0 │            │  0 │
...
```

每一行描述一列：

- `cid`：列的序号
- `name`：列名
- `type`：类型
- `notnull`：1 表示不能为空，0 表示可以为空
- `dflt_value`：默认值（阶段 2 讲）
- `pk`：0 表示不是主键。非 0 表示是主键的组成部分，数字是它在主键里的位置。如果主键由多列组成，就会看到 1、2……

`PRAGMA` 是 SQLite 专有的命令，用来查询或设置数据库的内部信息。它和 SQL 语句一样要以**分号**结尾，这一点和 `.tables` 这类点命令不同。

### 4. 在 DBeaver 里看

左侧导航中双击表名，打开「属性」标签页，列出的信息和 `PRAGMA table_info` 一样，只是换成了图形界面。

### 5. 看看里面的数据

```sql
SELECT * FROM Track LIMIT 5;
```

意思是"从 `Track` 表取出所有列（`*`），只要前 5 行"。这条语句先当作偷看数据的工具来用，`SELECT` 的正式讲解在 0.4。

建议先执行这两条命令，让输出更好读（每次进入 sqlite3 都要重新设置一次）：

```
.headers on
.mode box
```

## 参考答案与讲解

下面的数据都是在 `data/chinook.db` 上实际查出来的。每题先给结论，再讲为什么。

### 第 1 题：Customer 的结构

**命令**（任选一个）：

```
sqlite> .schema Customer
sqlite> PRAGMA table_info(Customer);
```

在 DBeaver 里双击 `Customer` 打开「属性」页，看到的是同一份信息。

**结论**：

- 主键是 `CustomerId`。`PRAGMA` 结果里只有它的 `pk` 是 1，DBeaver 里只有它带钥匙图标。
- `NOT NULL` 的列有 4 个：`CustomerId`、`FirstName`、`LastName`、`Email`。

**易错点**：`Company`、`Phone`、`Country` 这些列都可以为空。不能看到一列「看上去每个顾客都该有」，就以为它是 `NOT NULL`。能不能为空以表结构里的声明为准，不看数据长什么样。

### 第 2 题：主键为什么用 CustomerId

**为什么不用 `FirstName`**：

```
sqlite> SELECT CustomerId, FirstName, LastName FROM Customer WHERE FirstName = 'Frank';
16 | Frank | Harris
24 | Frank | Ralston
```

主键必须**唯一**，而名字天然会重复。如果用 `FirstName` 当主键，第二位 Frank 根本插不进来，DBMS 会拒绝。即使换成「名 + 姓」，世界上同名同姓的人也多得是，照样不能保证唯一。

**`Email` 能不能当主键**：从两个角度看。

1. **会不会重复？** 现在 59 位顾客的 59 个邮箱确实互不相同。但这只是**当前数据**碰巧没有重复。主键要求的是**规则上永远不重复**，比如一家人共用一个邮箱注册两个账号，业务上允许不允许？这得由业务来定，数据库保证不了。另外，`NOT NULL` 只保证「不为空」，不保证「不重复」，这是两条不同的规则。
2. **会不会变？** 这是更关键的一点。顾客会换邮箱。主键会被别的表引用，比如 `Invoice` 表用 `CustomerId` 记录每张发票是谁的。如果主键是邮箱，顾客一换邮箱，`Invoice` 里所有引用它的行都得跟着改，又回到了 [0.2](0.2-为什么需要数据库.md) 问题五「改一处漏一处」的老问题。

`CustomerId` 只是一个编号，**没有业务含义**，所以它永远没有理由改变。这就是 Chinook 几乎每张表都用整数编号当主键的原因。

如果业务确实要求「邮箱不能重复」，可以单独给 `Email` 加一条「唯一」约束，不必让它当主键（约束在阶段 2 讲）。主键怎么选，阶段 1 会正式讨论。

### 第 3 题：两列组成的主键

**表**：`PlaylistTrack`，主键是 `(PlaylistId, TrackId)`。

```
sqlite> .schema PlaylistTrack
CREATE TABLE [PlaylistTrack]
(
    [PlaylistId] INTEGER  NOT NULL,
    [TrackId] INTEGER  NOT NULL,
    CONSTRAINT [PK_PlaylistTrack] PRIMARY KEY  ([PlaylistId], [TrackId]),
    ...
```

用 `PRAGMA table_info(PlaylistTrack);` 看，两列的 `pk` 分别是 1 和 2；在 DBeaver 里，两列都带钥匙图标。

这张表的每一行表示「某个歌单里有某首歌」。用数据说话：

| | 数量 |
|---|---|
| 总行数 | 8715 |
| 不同的 `PlaylistId` | 14 |
| 不同的 `TrackId` | 3503 |

- **只用 `PlaylistId` 不行**：14 个歌单却有 8715 行，一个歌单里有很多首歌，同一个 `PlaylistId` 会出现很多次，不唯一。
- **只用 `TrackId` 也不行**：3503 首歌却有 8715 行，同一首歌可以被收进好几个歌单，同一个 `TrackId` 也会出现多次。
- **两列合在一起**：唯一的是「哪个歌单 + 哪首歌」这个组合，它保证了**同一首歌不会在同一个歌单里出现两次**。

像 `PlaylistTrack` 这样专门用来记录「多对多」关系的表（一个歌单有多首歌，一首歌在多个歌单里），阶段 1 设计选课系统时会再遇到：一个学生选多门课，一门课有多个学生。

### 第 4 题：手动追踪 TrackId = 3

| 第几步 | 查的表 | 找哪一行 | 读到什么 |
|---|---|---|---|
| 1 | `Track` | `TrackId = 3` | 曲名 **Fast As a Shark**，`AlbumId = 3` |
| 2 | `Album` | `AlbumId = 3` | 专辑 **Restless and Wild**，`ArtistId = 2` |
| 3 | `Artist` | `ArtistId = 2` | 艺术家 **Accept** |

**易错点**：编号在第 2 步变了，从 3 变成了 2。讲解里举的 1 号曲目例子恰好一路都是 1，容易让人以为「同一个编号一直往下查」。每一步都要用**上一步读到的那个外键值**去下一张表里找。

### 第 5 题：员工的上下级关系

`ReportsTo` 引用的是 **`Employee` 表自己**：

```
FOREIGN KEY ([ReportsTo]) REFERENCES [Employee] ([EmployeeId])
```

每个员工的 `ReportsTo` 存的是他上级的 `EmployeeId`。外键引用自己所在的表，这叫**自引用**。

```
Andrew Adams (1, General Manager)
├── Nancy Edwards (2, Sales Manager)
│   ├── Jane Peacock (3, Sales Support Agent)
│   ├── Margaret Park (4, Sales Support Agent)
│   └── Steve Johnson (5, Sales Support Agent)
└── Michael Mitchell (6, IT Manager)
    ├── Robert King (7, IT Staff)
    └── Laura Callahan (8, IT Staff)
```

**树根为什么是空的**：Andrew Adams 是总经理，**没有上级**，所以 `ReportsTo` 里没有可以填的值，就是 NULL（空）。

为什么不随便填个数？

- 填 `0`：没有编号为 0 的员工，等于引用了一个不存在的人，外键的意义就被破坏了。
- 填 `1`（他自己）：意思变成「他向自己汇报」，这是错误的信息。

NULL 表示「这里没有值」，这才是如实的记录。NULL 还有不少反直觉的地方，阶段 0 后面会专门讲。
